= Phorga Architecture Documentation (arc42)
:toc: left
:toclevels: 2
:sectnums:

== 1. Introduction and Goals

Phorga is a headless photo/video organizer and duplicate detector.
It runs as a daemon inside a Docker container, organizing media files by date metadata and detecting duplicates across multiple sources.

=== Requirements Overview

* Automatic date-based organization of photos/videos into configurable folder structures.
* Independent duplicate detection (metadata- and content-based).
* Primarily file-configured via YAML/JSON, with an optional built-in local/private web UI for configuration management.
* Docker-first deployment, multi-arch (amd64, arm64).
* Optional push notifications via ntfy.sh.

The product view is in link:../product.md[product.md]. The exact, testable requirements are in link:../specs/README.md[docs/specs] (IDs `ORG-*`, `DUP-*`, `CFG-*`, `NTF-*`, `WEB-*`, `RUN-*`). This document does not repeat them; it covers structure, runtime flow and deployment.

=== Quality Goals

[cols="1,3"]
|===
| Goal | Description

| Reliability
| File operations are atomic and never replace an existing file (hard-link publish). Jobs run one at a time. Single file failures do not abort runs.

| Resumability
| State is persisted; the daemon resumes where it left off after restarts.

| Simplicity
| No database, no frontend build chain, no external runtime dependencies beyond Docker. The optional web UI is part of the same binary.

| Portability
| Runs on Linux, macOS, Windows, and Synology NAS.
|===

== 2. Constraints

* Written in Go (pure Go, no CGO for cross-compilation).
* Configuration via YAML or JSON file remains the source of truth.
* Optional built-in web UI is intended for local/private deployment, not public exposure without additional protection.
* No GUI or REST API.
* State persistence via flat JSON files (no database).
* Docker as primary deployment mechanism.

== 4. Solution Strategy

* *Single binary, optional local web UI*: Organizer and Duplicate Detection are independent cron jobs within one process, run one at a time (ADR-0020); the same process can optionally expose a configuration web UI.
* *Cron-based scheduling*: Uses `robfig/cron/v3` for in-process scheduling. No external cron dependency.
* *Atomic, no-clobber file operations*: Media is written to a temp file and published with a hard link, which never replaces an existing file; moves within one volume are a link plus unlink (ADR-0006, ADR-0019).
* *Own readers for container formats*: Capture dates of HEIC and MP4/MOV are read by small pure-Go box walkers (ADR-0021).
* *JSON state files*: Simple, inspectable, corruption-tolerant state persistence.
* *Structured logging*: JSON-formatted `slog` output for observability.

[cols="1,3"]
|===
| Package | Responsibility

| `cmd/phorga`
| Entry point. `main` only wires SIGINT/SIGTERM to a context (and restores the default handling after the first signal, so a second one terminates); `run(ctx, args, logOut)` parses flags, loads and validates the config (or starts setup mode without one, CFG-009), registers jobs, starts the scheduler and the web UI (always when there are no jobs), and returns the exit code (0 ok, 1 error, 2 usage). The `engine` owns the configuration in effect: the web UI hands it a saved configuration, which it writes, reads back and puts into effect by swapping the scheduled jobs (CFG-008, ADR-0022). Tested end-to-end in `main_test.go`.

| `config`
| YAML/JSON loading, defaults, fail-fast validation.

| `exclude`
| Decides which entries below a source are skipped: the fixed system and hidden entries (`@eaDir`, `#recycle`, `#snapshot`, dot-names) and the user's `exclude` patterns. Used by the organizer, duplicate detection and the file count, and by `config` to validate patterns (ADR-0016).

| `scheduler`
| Cron wrapper. A job never overlaps with itself (TryLock per job name, kept across config changes), and only one job runs at a time (a one-slot semaphore; due jobs wait, ADR-0020). Jobs can be unregistered while running; the busy run finishes. Reports the next run and the running/waiting state per job, and computes next run times for the UI preview.

| `organizer`
| Recursive source scanning, date resolution, copy/move, lightweight duplicate handling.

| `dedup`
| Independent duplicate detection (metadata, or perceptual hash confirmed by a detail check), cross-source matching through an index (metadata buckets, multi-index hashing for pHash) instead of comparing every pair. One shared fingerprint cache (`<stateDir>/dedup-cache.json`) keeps pHash/EXIF results, the detail fingerprints of candidates and the resolution of group members for unchanged files between runs (ADR-0015, ADR-0017). Each duplicate group keeps its highest-resolution file (ADR-0018).

| `metadata`
| Date resolution: embedded dates (EXIF via goexif; HEIC `Exif` item and MP4/MOV `mvhd` via its own ISO box reader, ADR-0021), filename and path dates; file type detection; target path token resolution.

| `fileops`
| Atomic, no-clobber copy and move (hard-link publish, same-volume link moves, `…Replace` variants only for the organizer's `replace`), atomic writes of Phorga's own files, suffix generation (ADR-0019).

| `state`
| JSON state read/write with atomic saves and corruption recovery.

| `notify`
| ntfy.sh HTTP client, fire-and-forget with timeout.

| `runstatus`
| Last result per job for the status page. Persists non-dry results to `<stateDir>/run-status.json`; dry-run results stay in memory (ADR-0014).

| `synology`
| Finds Synology Photos users (`<homes>/<user>/Photos`) by reading folder names only, and builds the ready-made organizer profile for a user (SYN-001, SYN-002).

| `webui`
| Optional HTTP handlers, templates, localization, config save/validate flow, live previews, adding and removing entries and Synology Photos users in the form (`POST /ui/form`, WEB-015, SYN-003), collapsed cards with a flow summary (WEB-016), editing the config file as text (`/ui/yaml`, WEB-018), the read-only folder picker below `webUI.browseRoots` (ADR-0013), the status page, the help page with the setup guide in one template per language (`/ui/help`, WEB-022), and the embedded HTMX and stylesheet assets. All handlers sit behind the optional Basic-auth password (WEB-020) and Go's cross-origin protection (WEB-021). Gets job status from `main` through the small `StatusSource` interface, and applies a save through the `Apply` callback, or the edited file text through `ApplyRaw`, which writes it unchanged so comments stay (CFG-008, WEB-018).
|===

== 6. Runtime View

=== Start

`run` loads and validates the config (or starts setup mode without one), creates `stateDir` and checks that it can read every file below it and write in every folder of it (RUN-003). If not, it logs the folder and the uid it runs as and exits with code 1 before any job is scheduled: a `copy` job without its state would copy every file again on every run. Then it schedules the jobs and, if enabled, starts the web UI, warning when the config file cannot be replaced by a save.

=== Duplicate Detection Run

[plantuml, runtime-dedup, svg]
----
@startuml
start
:Cron triggers dedup job;
:Count supported files (for progress);
:Scan all sources recursively,\nskipping system, hidden and excluded entries;
repeat
  :Next supported file;
  if (Unchanged and in cache?) then (yes)
    :Take pHash / embedded date from cache;
  else (no)
    :Compute pHash or embedded date;
    :Store in cache;
  endif
repeat while (more files?)
:Prune vanished entries, save cache;
:Build an index (metadata buckets or
pHash chunk tables) and find each file's candidates;
if (content mode?) then (yes)
  :Confirm each pHash candidate by its detail
fingerprint (from cache or computed and cached);
endif
:Group matches; each group keeps the file with the
most pixels (header, cached), then the larger one;
:Collect duplicate pairs against the kept file;
repeat
  :Next duplicate pair;
  if (dryRun?) then (yes)

  else (no)

  endif
repeat while (more pairs?)
:Send ntfy notification;

@enduml

Files skipped by the fixed list or the job's `exclude` patterns (DUP-013, ADR-0016) are not scanned and not compared. Their cache entries are pruned like those of vanished files.

=== Shutdown

On SIGINT/SIGTERM, `run` returns and its deferred `Scheduler.Stop()` names the running jobs in the log, cancels the context that every job receives, stops cron from starting new runs, and waits for running jobs (logging every 10 s). Jobs that wait for the job slot return without running (RUN-002). The organizer and duplicate detection check the context between files (ORG-021, DUP-010). Cancelled runs are not recorded or notified. A second signal uses the OS default and terminates the process (RUN-001).

* Image: `mnrd001/phorga` on Docker Hub, multi-arch (`linux/amd64`, `linux/arm64`), tags `latest` and `sha-<commit>`. Built and pushed by `.github/workflows/docker.yml` after every merge to `main`, only after build, vet and test pass. Go cross-compiles in the build stage, and the runtime stage has no `RUN` steps, so no emulation is needed.
* Base image: `gcr.io/distroless/static-debian13:nonroot` (no shell; CA certificates and time zone data included). Runs as uid 65532 unless `user:` sets the NAS user. Images before 2026-11-21 ran as root on Alpine; their state volume belongs to root (README › Docker).
* State volume: `/data/state`
* Mount the common parent of source and target once (e.g. `/volume1/photos`) to get same-volume moves; Linux refuses hard links across mount points (ORG-025).
* Config mount: the folder `/config`, writable by Phorga's user, so the web UI can create and replace `config.yaml` atomically. A file mounted on its own cannot be replaced (EBUSY). The file may be missing at first (setup mode, CFG-009).
* Synology Photos users (optional): mount `/volume1/homes` at `/homes`. Phorga's user needs read access to the home folders it should list, and write access to the ones it organizes.
* Timezone via `TZ` environment variable.
* Web UI: the image sets `PHORGA_WEB_UI_ADDR=0.0.0.0:8080`, so the UI listens on all interfaces inside the container; the port mapping decides who can reach it (`127.0.0.1:8080:8080` publishes it on the host loopback only). It always starts while there are no jobs. Other devices reach it through a reverse proxy on the host, on a Synology the DSM reverse proxy (HTTPS, e.g. port 8443 → `localhost:8080`). `PHORGA_WEB_UI_PASSWORD` turns on HTTP Basic auth for every request (WEB-020, ADR-0023).

== 8. Crosscutting Concepts

=== Atomic File Operations
Media copies go to a temp file in the target directory. It is flushed, its size is checked against the source (ORG-019), and it gets the source's modification time (ORG-018). It then gets its final name with a hard link, which fails if the name is taken, so an existing file is never replaced, even one written by another program in the meantime (ORG-020, ADR-0019). Without hard-link support, the code falls back to check + rename. Moves within one volume are a hard link plus unlink, without copying (ORG-025); otherwise a move is a verified copy plus delete. Only the organizer's `replace` uses rename over an existing file. A transfer onto the source file itself is refused (ORG-024).

Phorga's own files (state, cache, run status, config) are written with temp file + rename and replace their previous version.

=== Error Resilience
* Single file errors are logged and skipped; the run continues.
* Single source failures do not block other sources.
* Notification failures are logged but never block runs.

=== State Management
* JSON files, one per source/job.
* Atomic writes (write temp → rename).
* The organizer saves the state at the end of a run and after every 200 processed files (ORG-015), never in a dry run.
* Duplicate detection keeps one fingerprint cache for all jobs, held by one in-process object with a mutex, saved every 500 new fingerprints and after each scan, also in dry runs (DUP-012, ADR-0015).
* Corruption triggers a warning and full re-scan (no data loss).

=== Structured Logging
* JSON-formatted via `log/slog`.
* All actions, skips, and errors are logged with context.

=== Configuration UI
An optional HTTP server in the main process renders templates with HTMX; all assets are embedded, so it works offline. It shows the configuration in effect, validates with the same rules as startup, and saves to the active file (applied at once, CFG-008) or a separate file (not applied). It is meant for local/private use only. The behavior is specified in link:../specs/web-ui.md[web-ui.md].

== 10. Risks and Technical Debt

[cols="1,3,3"]
|===
| Risk | Impact | Mitigation

| Large libraries
| The first content scan decodes every image
| The fingerprint cache avoids re-reading unchanged files (DUP-012). Matching uses an index, about 0.1 s for 100,000 hashes (DUP-004).

| pHash memory on NAS
| Memory spikes when hashing many large images
| Sequential processing, one image at a time. The detail check keeps one 4 KB thumbnail per candidate in memory during a run.

| Date reader gaps
| Some RAW files lack EXIF support in goexif; cameras that write local time into `mvhd` are shifted by the zone offset; Apple's `com.apple.quicktime.creationdate` is not read
| Graceful fallback to filename, path, mtime (ORG-002). `ignoreModTime` sends undated files to `fallbackFolder`.

| Filesystems without hard links
| On exFAT and some network mounts, publishing falls back to check + rename, so a file written by another program in that instant could be replaced
| Documented in README › Known Limits (ADR-0019). Phorga's own jobs no longer run in parallel (RUN-002).

| Jobs wait for each other
| A long duplicate detection run delays organizer runs and the reverse
| The status page shows waiting jobs; spread the schedules (ADR-0020).

| Local/private web UI only
| Whoever reaches the UI can change what Phorga moves, with immediate effect. One shared password, no lockout; over plain HTTP it is readable on the network. The folder picker reveals folder names below `browseRoots`.
| Optional password (WEB-020), start-up warning without one, cross-site writes rejected (WEB-021). The guide puts HTTPS in front and forbids internet exposure (ADR-0023). Keep `browseRoots` limited to the media folders.

| Access to all home folders
| Listing and organizing Synology Photos users means Phorga's user must read (and, for `move`, write) other users' home folders, a wider permission than a single photo share
| The UI marks users it cannot read as "no access" instead of failing. Mounting `/homes` is optional; users can mount single `Photos` folders instead.

| Settings change while a job runs
| After a save, a running job keeps its old settings until it ends
| Intended (ADR-0022): the next run uses the new settings; the save result says what needs a restart.

| Duplicated token list
| `targetStructure` tokens are defined in both `config` and `metadata`, so they can diverge
| Noted in ORG-009 and AGENTS.md. Candidate for refactoring into one list.
|===

== 11. Glossary

[cols="1,3"]
|===
| Term | Definition

| Organizer
| Feature that sorts media files into date-based folder structures.

| Duplicate Detection
| Independent feature that finds and handles duplicate media files.

| pHash
| Perceptual hash — a fingerprint of visual image content.

| Hamming Distance
| Number of differing bits between two hashes. ≤ 5 = duplicate candidate in content mode.

| Detail fingerprint
| 64×64 grayscale thumbnail of a pHash candidate. Two candidates are duplicates only when no tile of it differs in more than 12 % of its brightness steps (DUP-014).

| targetStructure
| Path template for the target folders, with tokens in four languages (ORG-005 to ORG-008).

| Embedded date
| The capture date stored in the file itself: EXIF in JPEG, RAW and HEIC, or the `mvhd` creation time in MP4/MOV. The only date the duplicate checks compare (ORG-011, DUP-002).

| fallbackFolder
| Destination for files where no date can be determined; reachable only with `ignoreModTime` (ORG-003).

| Dry Run
| Mode that logs planned actions without modifying files.
|===
